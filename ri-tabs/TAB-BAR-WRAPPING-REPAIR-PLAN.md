# Tab Bar Wrapping Repair Plan

## Goal

Fix `ri-tabs` so that file tabs are never visually clipped at the right edge of the frame. When the complete tab sequence does not fit on one row, the native Tab Bar must use as many rows as necessary, and it must shrink back to fewer rows when the frame becomes wider or tabs disappear.

The required behavior is:

```text
[-] foo.el   [-] bar.el   [-] very-long-name.odin
[-] baz.el   [-] main.el
```

instead of:

```text
[-] foo.el   [-] bar.el   [-] very-long-name.o...
```

or tabs silently extending beyond the visible right edge.

The existing content-sized tab labels and duplicate-name qualification rules must remain unchanged.

## Why the Previous Fix Failed

The previous implementation assumed that this configuration was enough:

```elisp
(setq-default auto-resize-tab-bars t)
```

while preserving whatever multiline value native redisplay might choose for:

```elisp
(frame-parameter frame 'tab-bar-lines)
```

That assumption is not valid for Ri's custom Tab Bar.

`ri-tabs` does not render normal workspace tabs through `tab-bar-tabs-function`. Instead, it replaces `tab-bar-format` with:

```elisp
'(ri-tabs--format-tabs)
```

and returns its own sequence of `menu-item` entries.

In Emacs's Lisp-side Tab Bar bookkeeping, `tab-bar--update-tab-bar-lines` derives the normal Tab Bar height from `tab-bar-show` and the native workspace-tab count and normally produces only `0` or `1`. Therefore Ri cannot rely on that code to discover how many rows its custom file-tab menu items require.

The tests added by the previous implementation only verified this artificial scenario:

```elisp
(set-frame-parameter frame 'tab-bar-lines 4)
(ri-tabs--refresh)
(should (= (frame-parameter frame 'tab-bar-lines) 4))
```

That proves that Ri does not overwrite an already-multiline value. It does **not** prove that anything ever changes the value from `1` to `2`, `3`, etc. in a real frame.

The repair must therefore make `ri-tabs` responsible for determining the required row count.

## Required Behavior

### 1. Ri computes the required number of rows

For every eligible graphical frame, Ri must determine how many rows are necessary to display all currently visible Ri tab items.

Conceptually:

```text
available frame width
        ↓
measure each complete tab
        ↓
pack complete tabs left-to-right
        ↓
start another row when the next tab does not fit
        ↓
set tab-bar-lines to the resulting row count
```

The calculation must never split a tab label between rows.

### 2. Wrapping is based on rendered width, not filename length

Do not use raw character counts such as:

```elisp
(length label)
```

as the primary layout metric.

Tab labels are rendered using proportional/font-dependent faces, markers, spaces, and possibly other display properties. The repair should use a pixel-width measurement available in graphical Emacs whenever possible.

Create a dedicated measurement helper, conceptually:

```elisp
ri-tabs--item-pixel-width
```

It should measure the actual displayed label, including:

- left/right padding generated by Ri;
- the marker (`[-]`, `[ ]`, `[:]`, `[÷]`);
- the space between marker and filename;
- the qualified filename label;
- the face used by that item where it affects metrics.

If an exact Tab Bar pixel-measurement primitive cannot be used directly, isolate the approximation in this helper so it can be corrected independently without changing the row-packing algorithm.

### 3. Add a deterministic row-packing function

Introduce a pure helper, conceptually:

```elisp
ri-tabs--required-row-count
```

Inputs should be sufficient to test it without a real GUI frame, for example:

```text
available-width: 500 px
item-widths:     (120 160 140 150)
```

Expected result:

```text
2 rows
```

Packing rules:

1. Begin with one row for every eligible Ri frame.
2. Add items in display order.
3. If the next complete item fits, keep it on the current row.
4. Otherwise increment the row count and place the whole item on the next row.
5. A single tab wider than the frame still occupies one row by itself; do not loop or create an empty row before it.
6. Zero visible items still leave the ordinary Ri Tab Bar at one row while the mode owns the surface.

### 4. Explicitly set `tab-bar-lines`

After calculating the row count, Ri must set:

```elisp
(set-frame-parameter frame 'tab-bar-lines required-lines)
```

Do not preserve an arbitrary old multiline value as the normal behavior anymore.

The previous rule:

```elisp
(when (< current-lines 1)
  (set-frame-parameter frame 'tab-bar-lines 1))
```

must be replaced with actual layout computation.

For structurally ineligible/auxiliary frames, keep:

```elisp
tab-bar-lines = 0
```

### 5. Keep `tab-bar-lines-keep-state` only for ownership protection

Ri still needs to prevent native workspace-tab bookkeeping from replacing its calculated height with `0` or `1`.

Therefore the likely policy is:

```elisp
(set-frame-parameter frame 'tab-bar-lines required-lines)
(set-frame-parameter frame 'tab-bar-lines-keep-state t)
```

But the implementation must verify this against Emacs 30.2.

The important change is that `keep-state` no longer means "wait for Emacs to resize the bar". Ri calculates the value first and then protects that value from unrelated native workspace-tab updates.

### 6. Stop depending on `auto-resize-tab-bars` for Ri wrapping

`auto-resize-tab-bars` must no longer be the mechanism that Ri depends on to discover multiline height.

Two acceptable outcomes are:

- leave the user's original value untouched because Ri no longer needs the variable; or
- preserve the existing save/restore behavior only if another native Tab Bar interaction still requires it.

Prefer removing Ri's forced:

```elisp
auto-resize-tab-bars t
```

if real testing confirms that explicit `tab-bar-lines` management makes it unnecessary.

Do not globally change this user option without a concrete need.

## Implementation Structure

### 1. Separate tab model generation from `menu-item` construction

Currently `ri-tabs--format-tabs` should be inspected for any logic that makes the final labels available only while constructing menu items.

Refactor minimally so the same ordered visible-tab model can be used for both:

- rendering the native `menu-item` list;
- measuring the displayed items for wrapping.

Do not duplicate the naming/disambiguation algorithm in the layout code.

There must be one source of truth for each final visible label.

### 2. Add frame width calculation

Introduce a helper, conceptually:

```elisp
ri-tabs--available-pixel-width
```

For graphical frames, use the real inner/native width available to the Tab Bar rather than `frame-width` in character columns whenever practical.

The helper must account for any fixed Tab Bar content that exists before or after Ri's tab list. With the current:

```elisp
(setq-default tab-bar-format '(ri-tabs--format-tabs))
```

there should be no native `+`, history, group, or alignment items unless Ri adds them itself, but this must be verified rather than assumed.

### 3. Add a single layout updater

Create a helper such as:

```elisp
ri-tabs--update-frame-layout
```

Responsibilities:

- return immediately for dead frames;
- set `tab-bar-lines = 0` for structurally ineligible frames;
- obtain the current visible Ri items for the frame;
- measure their widths;
- obtain available frame width;
- calculate the required row count;
- update `tab-bar-lines` only when the required value differs from the current value;
- set the appropriate `tab-bar-lines-keep-state` policy.

`ri-tabs--configure-frame` should handle lifecycle/eligibility configuration and delegate the dynamic height calculation to this helper.

### 4. Recalculate after all tab-content changes

`ri-tabs--refresh` must perform layout recalculation before forcing redisplay.

This covers:

- marking/unmarking;
- opening/closing buffers;
- saving/modification-marker changes;
- duplicate-name appearance/disappearance;
- repository/owner-context changes;
- selected-buffer changes.

Conceptually:

```elisp
(dolist (frame (frame-list))
  (ri-tabs--update-frame-layout frame))
(force-mode-line-update t)
```

Avoid recursive refresh/layout loops if measuring or setting frame parameters triggers hooks.

### 5. Recalculate on horizontal frame resize

Add a frame/window size hook appropriate for Emacs 30.2.

The resize handler must be cheap and should only update eligible frames whose usable width has changed.

Possible design:

```elisp
window-size-change-functions
```

or the more appropriate frame-size hook after checking Emacs 30.2 semantics.

The handler must cause:

```text
1 row → 2 rows → 3 rows
```

when narrowing, and:

```text
3 rows → 2 rows → 1 row
```

when widening, without requiring a buffer change.

If resize callbacks can occur repeatedly during interactive dragging, cache the last measured available width per frame and skip recalculation when unchanged.

### 6. Recalculate after font/theme changes when necessary

Pixel widths can change without filenames or frame dimensions changing, for example after changing the Tab Bar face/font or text scaling.

At minimum, ensure a normal Ri refresh remeasures widths rather than permanently caching item widths across unrelated display changes.

If testing shows theme/font changes leave stale wrapping until another Ri event occurs, add a narrowly scoped invalidation hook rather than a timer.

## Tests

The previous multiline tests are insufficient and should be replaced or supplemented with tests that prove Ri actually **computes** multiline height.

### 1. Pure packing tests

Test the row-count helper directly.

Examples:

```text
available 500, widths (100 100 100)       => 1
available 250, widths (100 100 100)       => 2
available 200, widths (100 100 100 100)   => 2
available 199, widths (100 100 100 100)   => 4
available 100, widths (150)               => 1
available 100, widths ()                  => 1
```

Also test exact-boundary behavior:

```text
available 200, widths (100 100) => 1
```

The algorithm must not wrap when an item ends exactly at the available boundary.

### 2. Frame layout test with stubbed pixel widths

Stub:

- available frame pixel width;
- per-item pixel widths;
- visible tab model.

Then call the real frame-layout helper and assert that it actively changes:

```elisp
tab-bar-lines: 1 -> 2
```

This is the regression test missing from the previous implementation.

### 3. Shrink test

Start with a simulated narrow frame requiring three rows, then simulate a wider frame and call the layout updater again.

Assert:

```elisp
tab-bar-lines: 3 -> 1
```

### 4. Refresh integration test

Stub layout inputs so the current tabs require more than one row, call:

```elisp
(ri-tabs--refresh)
```

and verify that the frame parameter changes automatically.

Do **not** pre-set `tab-bar-lines` to a multiline value in this test.

### 5. Resize integration test

Invoke the installed resize handler with changed frame width and verify that wrapping is recomputed even when:

- the selected buffer is unchanged;
- the marks are unchanged;
- no Ri command was run.

### 6. Auxiliary frame regression

Ensure structurally ineligible frames remain:

```elisp
tab-bar-lines = 0
```

regardless of measured item widths.

### 7. Existing behavior regressions

Run the complete `ri-tabs` ERT suite and retain coverage for:

- repository-owned marked sets;
- foreign-file qualification;
- same-repository duplicate basenames;
- non-Git owner contexts;
- content-sized labels;
- current/modified markers;
- new-frame setup;
- exact restoration when disabling `ri-tabs-mode`.

## Manual GUI Verification

Automated tests cannot fully prove native Tab Bar geometry. Add a manual verification scenario for Emacs 30.2 in a graphical macOS frame.

### Narrow-frame test

1. Start Emacs with `ri-tabs-mode` enabled.
2. Mark enough files to exceed one row.
3. Narrow the frame slowly.
4. Confirm that `tab-bar-lines` changes from `1` to `2` and then to higher values as required.
5. Confirm every complete tab remains visible.
6. Confirm no filename is shortened merely because of frame width.

### Wide-frame test

1. Starting from a wrapped state, widen the same frame.
2. Confirm the row count decreases automatically.
3. Widen until all tabs fit.
4. Confirm `tab-bar-lines` returns to `1`.

### Dynamic-content test

With the frame width fixed:

1. add a marked tab and confirm a new row appears when necessary;
2. remove a marked tab and confirm the extra row disappears when no longer necessary;
3. create/remove a duplicate basename and confirm changed qualification can independently increase/decrease the required row count.

### Mouse test on wrapped rows

Verify on every row:

- left-click selects the correct buffer;
- middle-click closes the correct buffer;
- right-click opens the correct context menu;
- hover/highlight applies to the intended complete tab.

This is important because manually setting `tab-bar-lines` is acceptable only if the native menu-item hit testing remains correct across wrapped rows.

## Fallback if Native Menu Items Still Do Not Wrap

Before finalizing the implementation, perform one minimal Emacs 30.2 experiment independent of Ri:

1. set `tab-bar-format` to a custom function returning many long `menu-item` entries;
2. explicitly set:

```elisp
(set-frame-parameter nil 'tab-bar-lines 2)
```

3. redisplay the frame.

If native graphical Emacs wraps those menu items correctly onto the second row, proceed with the explicit row-count implementation above.

If the second Tab Bar line is merely blank while the first line still clips, then the native menu-bar-backed Tab Bar cannot provide the required wrapping for Ri custom items. In that case, **do not keep adding heuristics around `tab-bar-lines`**.

Instead revise the implementation architecture to a renderer that supports explicit multiline layout while preserving Ri interaction semantics, for example a dedicated top-of-frame surface rather than the native Tab Bar menu-item flow.

This experiment is the first implementation checkpoint because it separates:

```text
"Ri failed to calculate the number of rows"
```

from the more fundamental possibility:

```text
"native Tab Bar custom menu items cannot wrap at all on this build"
```

## Acceptance Criteria

The repair is complete only when all of the following are true:

1. Opening/marking enough files in a narrow graphical frame automatically produces multiple visible Tab Bar rows.
2. No user or test needs to pre-set `tab-bar-lines` above `1`.
3. Every visible Ri tab remains complete rather than being clipped at the right edge.
4. Widening the frame automatically reduces the row count back to the minimum required value.
5. Removing tabs can reduce the row count without a frame resize.
6. Content-sized labels and duplicate-name qualification behave exactly as before.
7. Auxiliary frames still have no Ri Tab Bar.
8. The implementation does not depend on `auto-resize-tab-bars` magically discovering the height of Ri's custom file-tab sequence.
9. Tests verify actual `1 -> N` and `N -> 1` transitions produced by Ri's layout code.
10. A real graphical Emacs 30.2 manual test confirms the same behavior visually and confirms mouse interaction on wrapped rows.
